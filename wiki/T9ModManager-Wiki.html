How modding works

Cold War modding is nothing like Black Ops III. We do not have access to tools like Radiant, APE, LUA, etc.

Your mod is code-only. The launcher compiles it and hands it to the running game as if it were one of the game's own scripts, which then loads it along with everything else. It can call the same functions, use the same level variables and wait on the same flags.

Three consequences follow, and they shape everything else in this handbook:

  • A mod ends up as one script. A project of nineteen files has to become a single script before it can run. That is what the linker does, and it is why your function names get rewritten.
  • It lasts one map load. Load a new map and your mod is gone. Re-load it from the pre-game menu before every match.
  • Nothing can be registered late. Clientfields, UI models, weapons' assets. Anything the game seals when the map loads is closed to you. You can use what the game already declared, but you cannot declare a new one. Half the cannot-do list is this one fact wearing different hats.

Familiar with GSC?

If you have written GSC for an earlier Call of Duty, most of it carries straight over. Cold War's script VM grew out of the ones before it, so hashed #"istrings", function autoexec, ternaries and struct-returning waittill all work the way you expect. The tools do not carry over: no Radiant, no GDTs, no zone files, no share\raw to edit. One syntax difference catches people straight away: #using paths include the .gsc extension.

The starter script a new project gives you is a complete, working T9 mod:

#using scripts\core_common\flag_shared.gsc;

#namespace my_first_mod;

function autoexec main()
{
    level thread main_thread();
}

function private main_thread()
{
    // nothing you print before this line will be seen
    level flag::wait_till(#"intro_scene_done");

    IPrintLnBold("Script Loaded");
}

Four T9 idioms are already in there, and all four matter:

LineWhat it is doing
#using ...flag_shared.gsc; Brings in the namespace whose functions you call as flag::. The .gsc extension is required. Older games omitted it, Cold War does not, and without it the include quietly resolves to nothing.
#namespace my_first_mod; Your script's identity. It is also what the linker builds your function names out of, so it has to be unique across your project, and there are names it must not start with.
function autoexec main() The entry point. autoexec means “run this when the script loads”, which is the moment your mod is injected. Every mod needs exactly one.
flag::wait_till(#"intro_scene_done") The gate. Your script loads while the map is still coming up. Prints made then are thrown away and half the game state does not exist yet. Wait for this before doing anything visible.

Two habits to build now

Never do work in autoexec itself. Thread it and return, exactly as the template does. An autoexec that blocks holds up the script that included you.

Guard against being loaded twice. if ( isdefined( level.my_mod ) ) return; level.my_mod = 1; at the top of main() costs nothing and saves you the afternoon where everything happens twice.

Projects: a mod is a folder

A project is a folder under Projects/ next to the launcher, holding your scripts and a project.json. It is plain and unencrypted: ordinary files you can back up, diff, and edit with anything you like.

The entry script

One file is the entry: the one named after the folder, or failing that whichever declares function autoexec. It goes first when the project is linked, so the namespaces it establishes are the ones everything else resolves against, and it is the one file the tree will not let you delete.

Splitting a mod across files

NEW FILE in the project tree writes the file with its own #namespace and adds a #using for it to the entry script. From then on it is ordinary GSC: call into it as othernamespace::function(). 

// zm_classic_mod.gsc  (entry)
#using scripts\core_common\flag_shared.gsc;
#using zm_classic_mod\rounds.gsc;      <- written for you by NEW FILE

#namespace zm_classic_mod;

function autoexec main()
{
    level thread rounds::watch();          // a call into the other file
}

Those project-local #using lines vanish at build time

Your files are merged into one script before compiling, so an include pointing at another file of your own would be an unresolvable path in the finished script. The linker strips exactly those and leaves every real scripts\... include alone. You never have to think about it, but it is why a decompile of your published mod has fewer includes than you wrote.

Renaming

Use EDIT on the project card. A rename is four things at once: the folder, the entry script's file name, every project-local #using that referred to it, and the title. Doing it by hand in Explorer gets three of them.

The T9 GSC language

GSC is Treyarch's scripting language: C-shaped syntax, dynamically typed, cooperatively threaded. Cold War runs the newest version of it, with a few additions. If you have written GSC before you already know most of it, and everything in this section marked NEW is what changed.

Functions, self and level

Every function is declared with function. Two modifiers matter: autoexec (run this when the script loads) and private (not callable from another script. Use it for everything that is not part of your own file's surface).

A function called on an entity gets that entity as self. There is no this and no dot-call: the object goes before the call. 

function private give_points( amount )
{
    // self is whoever this was called on
    self.score += amount;
}

// called on a player:
player give_points( 500 );

// two special globals exist everywhere:
level.my_state = 1;        // level  - the match. Cleared on map load.
game[ "something" ] = 1;   // game   - survives a map load. Rarely what you want.

Threads

thread starts a function running alongside yours and returns immediately. A thread lives until it returns, until something it declared endon for happens, or until the entity it belongs to is deleted. 

level thread watch_rounds();          // runs on level
player thread watch_player();        // runs on the player
player childthread watch_gun();      // dies when the parent thread does

function private watch_player()
{
    self endon( #"disconnect" );   // stop when this player leaves
    self endon( #"death" );

    while ( true )
    {
        // ... do a thing ...
        wait( 0.5 );                 // seconds
        waitframe( 1 );              // or exactly one frame
    }
}

A loop with no wait hangs the game

GSC threads are cooperative. Nothing preempts them. A while or for that can go round without reaching a wait or waitframe freezes Cold War outright. The linter flags the obvious cases and the security scanner flags them again on submission, but the rule is yours to hold: every loop yields.

Notifies

The event system. Anything can notify, and anything can wait for it. This is how you hook the base game: the shipped scripts notify constantly, and most of what a mod does is listening. 

self waittill( #"death" );

// waittill returns a STRUCT of whatever was sent with the notify
result = self waittill( #"damage" );
amount = result.amount;

// with a timeout - returns undefined if it never fired
r = self waittilltimeout( 3, #"risen" );
if ( isdefined( r ) ) { /* it fired */ }

// sending one
level notify( #"my_mod_ready" );

Flags

A flag is a named latch on level. Waiting on one that is already set returns immediately, which makes flags the right tool for “has this happened yet” where a notify is the tool for “tell me when it happens”. 

#using scripts\core_common\flag_shared.gsc;

level flag::wait_till( #"intro_scene_done" );   // the one you will use most
level flag::wait_till( #"start_zombie_round_logic" );

if ( level flag::get( #"solo_game" ) ) { ... }

level flag::clear( "spawn_zombies" );            // pauses zombie spawning
level flag::set( "spawn_zombies" );

Hashed strings NEW

#"like_this" is a string the compiler turns into a number. The game uses them for nearly every identifier: notify names, model names, weapon names, asset names, table keys. They are cheap to compare and they are what the engine expects. When a function's parameter is named something like str_name in a decompile but every caller passes #"...", pass the hashed form. 

self setmodel( #"tag_origin" );
w = getweapon( #"ray_gun" );
level.zombie_health = 150;

You cannot build a hashed string at runtime

#"weapon_" + "upgraded" is not a thing. The #"..." is resolved by the compiler, not by the VM. Keep every variant as its own literal. And an ordinary string is not interchangeable with a hashed one: a function that hashes its argument will not accept "ray_gun", and one that wants a plain string will not accept #"ray_gun". When something silently does nothing, this is one of the first two things to check.

Arrays and structs

// arrays are dynamic and can be keyed by anything
a = [];
a[ a.size ] = "first";
b = [ 1, 2, 3 ];                     // inline init  NEW

foreach ( v in a ) { ... }
foreach ( k, v in a ) { ... }

// structs
s = spawnstruct();
s.origin = ( 0, 0, 0 );
s2 = { #origin: ( 0, 0, 0 ), #angles: ( 0, 90, 0 ) };   NEW

// arrays of the game's own things
players = getplayers();
foreach ( player in players ) { player thread my_thing(); }

Two array traps that have cost real sessions

getarraykeys keys do not index a different array. Keys pulled from one array and used to index another resolve to nothing. Comparing them (==, isinarray) is reliable, but indexing with them is not. Keep parallel arrays and scan linearly, or iterate by value (foreach ( s in level.zombie_weapons )).

An array the game built and keyed by hashed string cannot be indexed with a hashed string your script is holding in a variable. Same shape of failure: it resolves to nothing and your code takes the continue branch on every pass. Where the game keeps a flat list of the same fact, ask that instead with isinarray.

Comparison, and undefined

Any variable that was never assigned is undefined, and reading a field that does not exist gives you undefined instead of an error. Guard with isdefined(), and prefer the strict forms when either side might be undefined: 

if ( isdefined( self.my_field ) ) { ... }

if ( a === b ) { ... }        // strict - safe on mixed/undefined types
if ( a !== b ) { ... }

x = cond ? 5 : 10;             // ternary  NEW

Namespaces, names and traps

Two naming rules in T9 will let you compile a mod that does nothing, or refuse to compile a project while pointing at the wrong file. Both are cheap to avoid and expensive to diagnose, so they are near the front of this handbook instead of buried in troubleshooting.

Never start a name with a hash prefix

The compiler treats seven prefixes as hash literals. It expects hexadecimal after them, because that is how a decompile writes a name it could not resolve:

event_   var_   function_   namespace_   hash_   script_   file_

A function called event_halloween_main is not hexadecimal, so the whole thing compiles to hash zero. One of them compiles “fine” and is exported under the wrong name. Nothing can ever call it. Two of them in one script is a hard error: The export <name> was defined twice, reported against the second one, because they both became zero.

This bites hardest through your #namespace

The linker builds every exported name as <namespace>_<function>. So a single file declaring #namespace event_halloween; poisons every function in it and the project stops compiling, with an error naming a function, which points you at the wrong thing entirely. The namespace is the cause. Prefix yours with something of your own instead: t9_halloween, mymod_events.

Never name a local function the same as one you call through ns::

If a file both declares function on_ai_killed() and calls callback::on_ai_killed( &on_ai_killed ), the linker's rename pass rewrites the qualified call too, so the registration goes to a function in the callback namespace that does not exist. It compiles clean and does nothing at runtime: your mod loads, and silently has no behaviour.

The check is mechanical. For every function F your file declares, search the file for ::F(. If both appear, rename yours.

Namespaces must be unique in a project

GSC already forbids two scripts sharing a namespace, and the linker relies on that: it is the identity it prefixes your functions with. File names cannot serve, because every single-file mod ever published is called source_code.gsc. A script with no #namespace gets a stable invented one, which works but makes your own decompiles unreadable. Declare one.

Small ones, collected

  • No #define. It compiles, but your files are merged into one script before compiling and what that does to a define is untested. Use a function that returns the constant. The compiler folds it just as well and it survives linking.
  • A call to a function that does not exist compiles without complaint. somens::misspelled() is a link error at map load, not a compile error, and a link error is fatal. It is the one loud failure this VM has. The editor's linter catches the common shape of it (a namespace with no matching #using), but not a typo inside a namespace you did include.
  • Do not write the settings marker token in a source file, not even in a comment. The settings parser looks for markers deliberately and a marker inside a comment is still found in some positions. Describe it in prose if you must document it.
  • array::remove_undefined does not exist in T9's array_shared.gsc, whatever habits from older games say. Nor do plenty of other remembered helpers. Check it exists before relying on it, because a missing one is silent until map load.

The editor

A Sublime/VS Code-shaped editor that knows T9 specifically: it completes against a real database of the game's own functions, and it lints for the traps that have actually cost people a session.

Editing

  • Multi-caret and column selection. Shift+Alt+drag, or middle-button drag with no modifier at all (Sublime's binding). Both keep scrolling if you drag past the edge. A multi-caret edit is one undo step.
  • Folding and bookmarks live on the line, not on a line number, so they survive edits above them. The fold handle sits on function foo(), not on the {.
  • Snippets with mirrored tab stops, structural selection, line surgery, and a command palette on Ctrl+Shift+P.
  • SEARCH is a page of its own: this project, every project, or just what is open. Results are grouped by file, and REPLACE ALL works across them. It reads your unsaved buffers in preference to disk, so results match the screen.
  • Every binding is editable in VIEW › Edit Keybinds (Ctrl+K Ctrl+S), and the change reaches the menus, the palette and the exported shortcut sheet at once.

What it knows about the game

Completion and parameter hints come from a database built from a decompile of Cold War's own scripts: roughly 600 engine builtins, 97 namespace-to-include mappings and 4,033 game functions with their real parameter names. There are two databases (one for the server VM and one for the client), and which one answers is decided by the extension of the file you are typing in.

That is also where the missing-#using quick fix comes from: type clientfield:: in a file that has not included clientfield_shared.gsc and the linter offers to add it.

It is a derived subset, not the compiler's own table. A few real builtins are missing from it (getabsmins, useweaponmodel and even spawn among them). “Not in the database” is not evidence that a function does not exist. It just means nothing in the dump it was built from called it.

Player settings: the [[[ ]]] markers

This is the launcher's own system, and it is the single biggest thing you can do to make a mod worth downloading. A mod declares its options by writing markers into its own GSC. There is nothing to register and no API to call: the controls a player sees under your mod's description are generated from your source, and the values they pick are substituted back into it before it is compiled for them.

YOU WRITEA markerA declaration in your GSC saying what kind of control it is.
→
PLAYER SEESA controlUnder your mod in the library, with your label and your help text.
→
THEY CHOOSEA valueStored on their machine, keyed by your mod id. Survives your updates.
→
LOAD MODSA literalTheir value is written into your source as ordinary GSC, then compiled.

Form 1: inline, the declaration is the substitution point

Write the marker where the value goes. Good for a handful of options, because the declaration sits next to the thing it controls. 

level.infinite_ammo = [[[CHECKBOX id="infinite_ammo"
        label="Infinite Ammo" default=true]]];

level.zombie_speed = [[[SLIDER id="speed" label="Zombie Speed"
        min=1 max=10 default=5 help="Higher is faster."]]];

id= is required on this form. Everything else is optional.

Form 2: a header block, referenced by id

Declare everything in one place, then drop [[[id]]] wherever you need the value, as many times as you like, in any file of the project. This is the form to use once you have more than a few settings, and the one that makes a big mod's configuration readable. 

/*[[[SETTINGS]]]
CHECKBOX headshots   "Headshots Only"   default=false
SLIDER   speed       "Zombie Speed"     min=1 max=10 default=5
TEXT     welcome     "Welcome Message"  default="Have fun"
CHOICE   difficulty  "Difficulty"       options="Easy,Normal,Hard" default="Normal"
[[[/SETTINGS]]]*/


if ( [[[headshots]]] )
{
    level thread headshots_only();
}

level.zombie_speed = [[[speed]]];

player IPrintLnBold( [[[welcome]]] );

The block line is TYPE id "Label" attributes.... The label is optional and falls back to the id. The whole block is written inside a /* */ comment so the file still compiles in any editor, and the parser removes the comment wrapper along with it.

The two forms mix freely in one mod, and in one file.

What the compiler actually sees

For a player who left the defaults alone but dragged the speed slider to 7:

level.infinite_ammo = true;
level.zombie_speed = 7;

if ( false )
{
    level thread headshots_only();
}

player IPrintLnBold( "Have fun" );

Every marker becomes a GSC literal and the declaration block is removed entirely. What reaches the compiler is ordinary GSC with no trace of the system, which is why a setting can appear anywhere an expression can, including inside a condition, an array literal, or a function argument.

The rules to know before you rely on it

  • Declarations are read across the whole mod, not per file. Declare a setting in one script and use it in another. That is checked before your mod is published, and the editor's linter knows about your sibling files, so a cross-file reference is not called a typo. Two files declaring the same id is an error.
  • An unresolved marker is a hard error. The mod is not compiled, not packaged and not published. There is no partial substitution. A stray marker would fail on every machine that installed the mod, so it fails on yours first.
  • Values are treated as untrusted input. A slider outside its range is clamped, a choice not in the list falls back to the default, and text is escaped before it becomes a GSC string literal. A hand-edited config file cannot inject code into your mod: a value of evil" ); KillServer(); IPrintLnBold( " arrives as one harmless escaped string.
  • Values are stored per mod id, so a player's choices survive your updates. This is another reason not to change ids.
  • Do not write a marker token in a comment to “document” it. Describe it in words instead.

COMPILE uses YOUR defaults, not a player's choices

Your test builds substitute every marker at the default= you declared, and print what they used to OUTPUT. That is also what the review bot compiles. To test a different value, change the default and recompile, or set a test value in EDIT MOD's MOD SETTINGS tab, which shows the exact panel your players will see and lets you build against what is on screen.

Presets

A second block names whole configurations, so a player can pick “Classic” instead of setting eleven sliders. A preset is a complete configuration: anything it does not mention takes that setting's declared default=, because a half-applied preset would give two different games depending on what the player had already touched. 

/*[[[PRESETS]]]
// The way the mod is meant to be played.
PRESET "Classic" default help="How the mod is meant to play"
    headshots = false
    speed     = 5
    difficulty = "Normal"

PRESET "Brutal" help="For people who have already beaten it"
    headshots = true
    speed     = 10
    difficulty = "Hard"
[[[/PRESETS]]]*/
  • One preset may be marked default, and that is what a fresh install gets, so the shipped configuration is yours instead of whatever each individual default= happened to be. Only one is allowed, and a second is an error.
  • There is no preset bar until a mod asks for one. Declaring a block asks. So does the line PRESETS on, for a mod that wants players to save their own without shipping any. PRESETS off overrides both. Off is the default.
  • Players can save their own. Those live only on their machine, are never in your package, and are deliberately kept apart from the values so that RESET TO DEFAULTS cannot take them with it.
  • Your // comments inside the block survive the editor rewriting it.

Make your presets from the panel, not by hand

EDIT MOD's MOD SETTINGS tab edits your presets rather than just previewing them. Set every control to what you want, press SAVE AS, name it, and your project's own /*[[[PRESETS]]]*/ block is rewritten as a single undo step, in declaration order, comments intact. It picks the file that already holds a block. If two files hold one, it refuses and says so rather than guessing.

The build pipeline

Both paths (COMPILE in the editor, and LOAD MODS on a player's machine) run the same stages in the same order. The differences are which guard goes on and whose setting values go in.

STAGE 1SubstituteMarkers replaced with literals and the SETTINGS block removed. Fails closed.
→
STAGE 2LinkEvery script in the mod becomes one, functions renamed to carry where they came from.
→
STAGE 3GuardA check spliced into the top of every function, so a mod cannot run where it should not.
→
STAGE 4CompileIn the launcher, to a compiled script.
→
STAGE 5LoadHanded to the running game.

When a player loads several mods at once there is one extra stage between 2 and 3: the already-linked mods are linked again, together, so the whole selection becomes a single script. That is what makes multi-mod loading work, and it is why two mods that both define #namespace utils is a problem the player finds, not you.

Every stage runs once per side. A mod with a client half is two scripts in two virtual machines, so it is linked twice, guarded twice and compiled twice. Settings are the exception: they are parsed across the whole mod, because one mod has one set of settings and a .csc may reference an id declared in a .gsc.

The linker

A mod is a folder, but the game takes one script. The linker reconciles those two facts, and it is the stage most likely to surprise you, because it renames your functions.

Naming

Every declared function becomes ModName_ScriptNamespace_FuncName, so give_all in the zm_perks namespace of a mod called Director's Cut becomes DirectorsCut_ZmPerks_give_all. Call sites are rewritten to match, including ns::func() cross-file calls and &func function references.

Two consequences for you: your #namespace must not start with a hash prefix, and you must not name a local function the same as one you call through another namespace. Both are in Namespaces, names and traps, and both are silent.

Your #using lines

Project-local includes (#using myproject\rounds.gsc;) are stripped, by exact relative-path match only. Never by file name: that would strip a real #using scripts\zm_common\load.gsc from any project that happens to own a load.gsc. Every genuine scripts\... include is left exactly as you wrote it and folded with the duplicates.

Order matters

The entry script goes first, then everything else in path order. So the file that declares your autoexec and lists its dependencies is the one that establishes the namespaces the rest resolve against. Alphabetical order would put audio.gsc ahead of the file that says the project uses it.

What comes out

One script, with duplicate #using lines folded together, every #namespace dropped and a single #namespace t9mm_linked; emitted in their place. If you ever decompile your own published mod, that is why it does not look like what you wrote.

Compiling

The launcher compiles GSC itself. There is no external tool to install, no command line step and nothing to configure: Ctrl+B builds the whole project and Ctrl+F5 builds it and loads it into the running game.

Which virtual machine a file is compiled for comes from its extension and from nothing else. A .csc builds for the client VM, and everything else builds for the server VM, which is what every mod written before client support existed is. There is no setting for it.

You never have to think about the compiled file

Compiled output is scratch. It is written, used and deleted. A published mod carries your source, which is also what a reviewer reads, and it is compiled fresh on each player's machine with their own setting values. There is nothing to ship, nothing to check in, and no compiled artefact to keep in step with your source.

Reading compile errors

A compile error names a file and a line you recognise, and clicking it opens that file there. Knowing why that is not trivial explains the one case where it cannot.

A line number from the compiler counts lines in what the compiler was handed: your whole project, linked into one script, with a guard spliced into every function and settings substituted throughout. Three stages moved your lines, so each hands back a record of where every line came from, and those are composed to answer “which file, which line, as the author typed it”.

“(combined script, line N)”

When an error lands on a line that belongs to no file you wrote (the linker's own banner, a guard helper), it is reported exactly like that instead of being given a plausible-looking location. A wrong jump is worse than no jump. In practice it means the error is not in your code and something upstream has gone wrong. The OUTPUT tab shows the raw compiler text beside it.

Compiler findings land in PROBLEMS, kept separate from the linter's list, since relinting happens on every keystroke and would otherwise wipe out the list you are working through. One click on a row jumps to it.

The errors you will actually see

MessageCause
The export <name> was defined twice Usually not a duplicate at all: two names starting with a hash prefix, both collapsing to zero. Check your #namespace first.
A parse error on a line that looks fine Look for a unary minus in a call argument (fn( -x )) on that line or the one before.
An error in a file you did not touch The linker merges everything, so a broken file anywhere in the project fails the whole build.

Client scripts (.csc)

Cold War runs two script virtual machines. .gsc is the server side (game logic, spawning, damage, points) and runs only on the host. .csc is the client side, running on each player's own machine: HUD, visual effects, sound, anything local. The launcher builds and loads both.

Put a .csc in your project and it is picked up automatically. Nothing else needs saying: no setting, no manifest, no pairing.

Confirmed working from an injected client script

  • function autoexec main(), runs at load time. The whole premise.
  • getlocalplayers(), and .origin off it.
  • util::spawn_model( localclientnum, #"model", origin ), a client-only visual, and the best heartbeat you can give yourself while probing.
  • playsound( localclientnum, alias, origin ).
  • getcurrentweapon( localclientnum ), but the weapon table may not be populated the instant you load, so poll with a bounded wait.
  • Ordinary #using + namespace calls into the game's own live client scripts.
  • Its own level, separate from the server's, useful for a re-injection guard.

The two VMs cannot call each other

An injected .gsc cannot call into client scripts and an injected .csc cannot call into server scripts. The only channel between them is the clientfield system, and you can only set fields the game already registered, never add one. So anything your client half needs to know, it usually has to work out locally: watch the local player's own weapon rather than having the server tell you about it. See What you cannot do.

Everything from the server side about timing carries over: prints and one-shot state writes made during the load window are lost, dev blocks do not exist, and loading is per map load. Guard against being loaded twice with if ( isdefined( level.my_mod ) ) return; on this side too. It is a different level, so it needs its own guard.

Loading a mod into the game

Your compiled script is handed to Cold War while it is running, and the game loads it along with its own scripts for that map. Everything about testing a mod follows from when that is allowed to happen.

The window is the pre-game menu

Too early (before a map and mode are chosen) and there is nothing to load into: you get “SPT pool is empty”. Mid-match is worse: it is reported as succeeding and nothing runs, because the match's scripts were linked long ago and never look again. Get to the lobby where the map is chosen and the match has not started, and load there.

The rules

  • Once per map load. Every map change (including a restart) wipes your mod. Go back to the menu and load again. This is not a bug and there is no way around it.
  • You have to be the host. A published mod runs in any match you host. A build made in the editor runs solo, or in a match holding nobody but you and your registered co-authors. Nothing here reads the lobby type (no script can tell a private lobby from a matchmade one), so the only question either guard asks is who is in the game. See below.
  • The host loads the server half. In co-op only the host runs .gsc, so only the host needs a server-side mod. A .csc half only affects the machine that loaded it. Every player who wants the client effects has to load it themselves.
  • Selection order is load order, and load order is priority. When two mods touch the same thing, the later one wins. Players can drag the list to change it, and the launcher warns about likely collisions but never blocks a load.
  • Unloading only works in the same window loading does, at the menu, before the match's scripts have run. Mid-match there is nothing to undo, and after a map load the slot is clean anyway.

The loop you will settle into

  1. Edit. Ctrl+B until it compiles.
  2. In game: quit to the pre-game menu (not the desktop).
  3. Ctrl+F5.
  4. Start the match. Watch for your gated print.
  5. Quit to the menu. Repeat from 1. You do not need to restart Cold War between builds, only between matches.

Where a mod is allowed to run

One guard, on unreleased builds only: a check inserted at the top of every function in your mod. A guarded function does nothing and returns, so a whole mod goes quiet without anything having to unwind it.

Your test builds, made in EDIT MOD

SOLO runs.
CO-AUTHORS ONLY runs.
ANYONE ELSE never.

Anyone who joins who is not a registered co-author ends the session. An untested build is not something to be playing on strangers.

Your published mod, downloaded and loaded

ANY MATCH YOU HOST runs.

A published mod was reviewed and signed to get onto the MODS page at all: that is its gate, not the lobby type. In public matchmaking it rarely amounts to much: the mod only runs when you end up as the host, loaded from the pre-game lobby, so a match you join in progress stays unmodified.

Why the test-build guard checks people, not lobby types

Not “is this an online session”. In Cold War every lobby launched from the menu is an online session, solo included, and the script can measurably not tell a Private co-op lobby from a matchmade one either. Every signal it can read returns the same values in both. So the guard asks the one question that can be answered: who is in the game. Solo passes outright. Anything else has to hold nothing but you and registered co-authors.

Practical consequences for you

  • Test builds run solo, or in a match holding nobody but you and your registered co-authors. Nowhere else. How you arrange that lobby is your business: the guard never looks at the lobby type, because it cannot.
  • Functions the guards generate all start __t9_. Seeing them in a decompile of your own test build is this, not your code.
  • Never paste them into your source. The security scanner flags it, because shipping the test guard would kick people who joined your published mod.
  • Every guarded function waits on the session state before doing anything, so a test build has a slightly different timing profile from a released one. If something is timing-critical, that is worth remembering.

Testing with co-authors

Two people cannot test one unreleased mod together unless the guard knows who they are. Setting that up is four steps:

  1. The owner invites from COLLABORATORS on the project card.
  2. The invited person accepts, in their own launcher. Being made co-author of somebody else's mod is a thing that happens to you, not something that can be asserted about you.
  3. Each co-author presses LINK MY ACTIVISION ACCOUNT, with Cold War running and signed in. It takes a few seconds and marks their row LINKED.
  4. The owner reopens COLLABORATORS (that is what fetches the current list) and rebuilds. The new build recognises everyone who has linked.

Then: the host is always allowed and never needs to register, a recognised co-author can join at any point (including late), and anybody else who joins ends the session.

What is stored

Only a one-way hash of the account id, never the id itself, and never a name. It is stored in your project and in the mod's published record, and it is what the guard compares against. Nothing identifying appears in the compiled script, so it is also not something a decompile of your test build gives away.

The console log

MOD TOOLS can show Cold War's own console output in a CONSOLE LOG tab, which is the closest thing to a real debugger you get. Everything your script prints goes there along with the game's own output.

The panel opens on a running script, not on a successful load, and that distinction is the whole design: a mid-match load reports success and runs nothing, so “we loaded something” is not evidence. Each build carries a one-off marker, and the panel stays locked until it sees that exact marker come back out of the game.

So an empty CONSOLE LOG after a load that said it succeeded is almost always the gate doing its job: you loaded mid-match. Go back to the menu.

When a mod does nothing

The retail VM fails silently. Internalise this one.

Divide by zero returns zero. A call to a function that does not exist does nothing. Reading a field that is not there gives you undefined and your code carries on with it. Deep recursion dies quietly at around 58 frames. There is exactly one loud error: a link failure, a call to a name that resolves to nothing at map load, which is fatal and immediate.

So: if your mod does nothing and nothing is on screen, suspect a name, a hash, or a wrong argument type long before you suspect the launcher.

The order to check things in

  1. Did it run at all? Put an ungated IPrintLnBold as the first line after your intro_scene_done wait. No print means the script never ran: you loaded mid-match, or a guard refused the lobby.
  2. Did it get past the gate? Print immediately before and after every flag::wait_till and waittill. Waiting forever on something that will never fire is the second most common cause, and it looks exactly like not running at all.
  3. Is the value what you think? IPrintLnBold( "x = " + x ). Almost everything in GSC concatenates into a string, including undefined, which prints as nothing at all. A print that comes out as "x = " has told you something.
  4. Is it a hashed-string mismatch? Passing "name" where #"name" is wanted, or the reverse, silently resolves to nothing. Check what the game's own callers pass.
  5. Is it a name the linker rewrote? See Namespaces, names and traps: a callback registered through a rewritten name compiles clean and never fires.

Printing, properly

  • IPrintLn for a build log, IPrintLnBold for one fact. Bold is one line that replaces itself, so a burst of bold prints shows you only the last one.
  • A print reaches the screen on the next server update, so a crash eats every print made in its own frame. If you are hunting a crash, put a waitframe( 1 ) after each diagnostic print. Without it, the last line on screen is a lie about where you got to. That single frame can cover hundreds of calls.
  • Bisect with prints, not with reasoning. A crash lands later than the call that caused it, sometimes much later. Halving the mod is faster than reading it.

Reading an actual crash

Cold War writes its own crash reports to %LOCALAPPDATA%\Activision\Call Of Duty Black Ops Cold War\crash_reports\ as zips. The info.json inside names the map, the mode and a crash signature, and that is usually enough: the same signature on two different maps means the same engine call with a different asset, which points straight at something you named that this map does not have.

Cookbook: timing and lifecycle

Every entry in this cookbook was paid for by something that did not work in game. Start here, because more mods are broken by when they ran than by what they did.

Your script loads during the loading screen

autoexec runs as the map comes up, before any client is listening and before most of the game's own state exists. Everything you do in that window is at risk:

  • Prints are thrown away. Nobody is there to receive them.
  • One-shot events are thrown away for the same reason. See Effects, where this is the whole explanation for “my effects never render”.
  • State you read may not exist yet. Weapon tables, zone tables, spawn structs and player entities all populate on their own schedule.

So the shape of every mod is the same: thread out of autoexec, wait, then work.

function autoexec main()
{
    if ( isdefined( level.my_mod ) ) return;   // loaded twice
    level.my_mod = 1;

    level thread run();
}

function private run()
{
    level flag::wait_till( #"intro_scene_done" );

    // from here on the match is real
}

Doing something to every player, including late joiners

getplayers() at one moment is a snapshot, and in co-op it is usually the wrong one. Register a connect callback as well, and you cover both. 

#using scripts\core_common\callbacks_shared.gsc;

function private run()
{
    level flag::wait_till( #"intro_scene_done" );

    foreach ( player in getplayers() )
    {
        player thread setup_player();
    }

    callback::on_connect( &on_connect );
}

function private on_connect()
{
    self thread setup_player();
}

function private setup_player()
{
    self endon( #"disconnect" );

    // ... your per-player work ...
}

Do not name a local function the same as the callback you register

The example above is deliberately on_connect registering &on_connect in a file that declares it, which is exactly the shape that silently breaks when the qualified form callback::on_connect is used with a same-named local. Written as above (unqualified callback:: import, local named differently from anything you call through ::) it is fine. If you ever write callback::on_ai_killed( &on_ai_killed ) next to function on_ai_killed(), rename yours.

Deleting an entity kills the thread it is called from

entity delete() frees the entity and terminates every thread whose self it is. So this never reaches its second line: 

self delete();
level thread do_the_thing();   // NEVER RUNS

Start the follow-up first, and retire the model with deletedelay() (end of frame) rather than delete(). That is what the game's own “consume this prop and spawn something” flows do, and it is worth treating as the rule for any such pair. The visible half (effect, sound) fires either way, so the bug looks like “the second half never happened” with nothing to point at.

Cookbook: players

Freezing, hiding the HUD, disabling things: use val::

scripts\core_common\values_shared.gsc, namespace val, is a reference-counted way to set player state, keyed by a cause. This matters more than it sounds: the game freezes controls on spawn, freezes them again for the black screen, and quest scenes freeze them a third time. A bare freezecontrols( 0 ) releases somebody else's lock, and a bare HUD-visibility call puts back a HUD another system deliberately hid. 

#using scripts\core_common\values_shared.gsc;

self val::set( #"my_mod", "freezecontrols", 1 );
self val::set( #"my_mod", "show_hud", 0 );

// give it all back - one call, no matching list to maintain
self val::reset_all( #"my_mod" );

Points and currency

Set points through the score system, not by writing the field. A player's score lives in two places, and writing only the visible one loses the value the moment they go down: 

#using scripts\zm_common\zm_score.gsc;

player zm_score::function_c1f146ff( 25000 );     // sets score AND the persistent copy

if ( player zm_score::can_player_purchase( cost ) )
{
    player zm_score::minus_to_player_score( cost );
}

Salvage is map-specific. Only some maps load the salvage system at all, so its fields are simply undefined elsewhere. Test with isdefined instead of inventing a currency the map has no use for.

Weapons

#using scripts\zm_common\zm_weapons.gsc;

w = getweapon( #"ray_gun" );

if ( w !== level.weaponnone )                       // it resolved
{
    if ( player zm_weapons::has_weapon_or_upgrade( w ) )
    {
        player zm_weapons::ammo_give( w );
    }
    else
    {
        player zm_weapons::weapon_give( w, 0, 1, undefined, undefined, #"white" );
    }
}
  • Do not reimplement zm_weapons::get_guns(). Call it. A hand-written copy of its filter gets the edge cases wrong, and note that its list keeps field upgrades, which you usually want to drop.
  • Iterate level.zombie_weapons by value (foreach ( s in ... )), never through getarraykeys. Each entry carries .weapon, .cost, .hint, .weapon_classname and .is_wonder_weapon.
  • Every wonder weapon is loaded on every zombies map, and you can register one on a map it does not normally appear on, but its audio will be missing and that cannot be fixed from script.

Give a player an item through the inventory, not by dropping one at their feet

Dropping a world item near a player produces something that frequently never becomes pickupable. The route that works is the inventory path the game uses itself: resolve the item entry, ask how many are held, set the amount, resolve the slot, and hand it over. It is more calls, and it is the difference between a mod that works and one that works on your machine.

Two gotchas that look like your code being wrong

  • The mystery box notifies before it gives. The “player grabbed a weapon” notify fires and only then does the give thread start, so for the next second getcurrentweapon() is still the gun they walked up holding. A check that judges the first frame and returns misses every box grab. Poll the whole delivery window. (The wall-buy notify is the opposite: it fires after the give.)
  • The perk-machine gate is self.num_perks, and the vending path never touches it. Buying perks from machines leaves it at zero on a vanilla player, by design. Any mod that “keeps the count honest” by setting it to the number of perks held silently kills every vending machine: the prompt still shows, the purchase is denied. Leave it alone.

Cookbook: putting things in the world

A model and a use prompt: the primitive that works

Spawn a script_model, put a trigger_radius_use in front of it, and hang a callback on the trigger. That is what the game's own interactable machines are, and it works from an injected script on any map. 

#using scripts\core_common\callbacks_shared.gsc;

model = spawn( "script_model", origin );
model setmodel( #"p9_fxanim_zm_gp_armor_station_xmodel" );
model.angles = angles;

// 24 units forward of the model, 50 up; radius 64, height 128
trigger = spawn(
    "trigger_radius_use",
    origin + anglestoforward( angles ) * 24 + ( 0, 0, 50 ),
    0, 64, 128
);

trigger.scriptmodel = model;
trigger setcursorhint( "HINT_NOICON" );
trigger sethintstring( #"hash_614130df578d98f0" );
trigger setvisibletoall();

trigger thread watch_use();

Do not build these as unitriggers

The unitrigger system builds a real trigger per player, and only when that player changes zone into the one the stub belongs to. A stub whose zone is unset, or whose zone nobody crosses into, silently never becomes a trigger, forever, with no error. Measured in game: three plain trigger_radius_use machines appeared, and ten wall weapons built exactly per the game's own dynamic-wallbuy recipe appeared as nothing at all, because nobody changes zone in the room they are already standing in. Use plain triggers unless you have a specific reason not to.

For a weapon prompt, setcursorhint( "HINT_WEAPON", w ) is what draws the weapon name and icon, not the hint string.

The four Outbreak-style stations work on every zombies map

Wunderfizz, the armor station and the weapon station (Pack-a-Punch level, rarity and ammo mods) are all spawnable from script on any zombies map. Their models are in the shared zombies asset table, and the LUI menu each one opens is registered on every zombies map even though only Outbreak spawns them.

The weapon station is the whole Pack-a-Punch answer for a mod that wants one somewhere new: relocating a classic map's own PaP means moving an animated barrier wired into that map's power and quest state, and the station is not. Guard each one on the menu handle it needs rather than assuming it exists.

Placing something so it is actually reachable

Picking a spot is harder than it looks, and every rule here comes from a machine that ended up inside a rock, under the map, or off a ledge.

  • A walk test answers “could you walk here”, never “does the thing fit”. It is one line at one height: a tree trunk 30 units to the side is never touched, and a rock lower than the trace height is walked straight over. A claimed spot needs a clear cylinder: 8 bearings × 3 heights (ankle, waist, head) out to the radius your model needs. A trace that starts inside geometry returns zero, so the same sweep also catches “this spot is inside a rock”, which nothing else detects.
  • Probe downward from well above. A ground trace that starts only a little above an estimated height starts inside solid when the real surface is higher (a kerb, a slab, a sloped yard) and does not stop at the surface over its head. It finds the next floor down. That is how a placed object ends up in the basement. Start ~96 units up, and refuse a hit more than one step below your reference rather than trusting it.
  • Try a bearing sweep and a list of distances, not one bearing and one distance. Keep every claimed spot in one array with a minimum-separation test. Two 64-radius use triggers 45° apart end up inside one another.
  • Ask the game whether a point is playable with zm_utility::check_point_in_playable_area( origin ) rather than inventing your own bounds, and get a zone name with zm_zonemgr::get_zone_from_position( origin, 1 ).

Do not refuse a spot just because you cannot name its zone

Spawn structs do not all carry a zone name, and code that returns “no” when it cannot identify one refuses every spot on any map that does not populate that field, which reads in game as your placement code silently doing nothing, on every map, forever. Fall back to the playable-area test.

Locking players in, and other blunt instruments

  • To lock doors, disable the triggers. Do not price them. If your mod also hands out points, every price is affordable. And a door usually has a trigger on each side. Disabling one leaves the other buyable, so walk the siblings too.
  • To pause the rounds, clear the "spawn_zombies" flag. The game's own round logic waits on it every pass and the maps' quests clear it for scripted moments, so it is a pause the game already knows how to take. The round cannot end while it is clear.

Cookbook: effects, models and sound

“My effects never render” is the most common thing a new CW mod runs into, and it has one cause and two fixes.

Why a one-shot effect vanishes

playfx is an event. spawnfx is an entity. Your mod loads during the loading screen, before any client is listening, and an event is not resent to a client that arrives later. A model, by contrast, is replicated in every snapshot, which is why models always show up and effects appear not to work at all.

Two fixes, in order of preference.

1. Set a clientfield, do not name an asset

The general answer for any effect from an injected script

The powerup effect field is registered in both VMs and in the shared zombies scripts, so it exists on every zombies map. A powerup is nothing more than a script_model with setmodel( #"tag_origin" ) and that field set to a small integer. The map's own client script then picks the asset, plays it on the tag and keeps the handle, so it loops, there is nothing for you to resolve, and because a clientfield is replicated state rather than an event it also reaches a player who was still loading.

Values 1 and 2 only. Higher values read effects registered inside a conditional, and an undefined effect handed to the client's play call faults on every machine.

2. Use the looping-fx primitive

h = spawnfx( #"my/effect", origin, forward, up );
waitframe( 1 );
triggerfx( h );

That is the game's own Radiant looping-effect pattern, and it produces a real entity that persists instead of an event that is missed.

Naming an effect that is not there

One of these is silent and the other crashes the game

playfx on a missing effect silently does nothing. spawnfx on a missing effect dereferences the null and takes the game with it. So “playfx rendered nothing” usually means the asset is not on this map, not that the event was lost, and reaching for spawnfx to fix it turns a silent failure into a crash.

  • The only effects a server script can rely on are the ones in level._effect. Not “in the map's asset table”. That says the asset is loaded, not that script can name it.
  • fx::get is no help as a test. It returns the key it was given when the key is missing, so an unregistered effect comes back as a plausible-looking value that names nothing.
  • Effect names are hashes, not strings. Passing a plain string where a hash is expected is one of the two classic ways a perfectly correct effect call does nothing.

Asset tables are hints, not inventories

The shared zombies asset table lists content across all zombies modes, Outbreak included, so a row in it does not prove the asset is on the map you are testing. And the per-map tables are not the whole truth either: every powerup effect the client plays is in none of them, and powerups obviously drop everywhere. Treat both as hints. The only proof is a call that worked in game.

Models

  • Server-side attach on an actor replicates, so cosmetics you might reach for a client script for can often be done server-side instead. The game's own zombie armour does exactly this.
  • A model the map never loaded is invisible, with a working prompt and a working trigger. If your machine has a hint and no machine, that is what happened. Prefer models from the shared zombies table.
  • Effect prop models are not placeable geometry. Models whose names mark them as an effect's own props are loaded because the effect that places and animates them needs them. Spawned by hand they are a shape with no light, no depth and no motion.

Sound

Weapon audio lives in per-map sound banks, and there is no load-a-sound-bank builtin anywhere in the game. A script can name a weapon the map does not normally have, and its model will resolve, but its sounds will not exist and nothing you can write will make the engine load them. This is the same wall as custom models: script can name an asset, it cannot ship one.

Cookbook: zombies and rounds

Never enumerate AI, and never register for AI spawn events

getaiarray() and an on_ai_spawned registration hard-crash Cold War from an injected script. The crash lands later than the call that caused it, so it will not look like it came from there, which is why it is better to know this before you write it than after. The editor's linter flags both.

Hooking every zombie as it spawns

There is a free per-zombie spawn hook on level that the zombie spawn path reads and nothing that ships ever writes. It is the safe replacement for the spawn callback: 

level.var_9c55db3 = &on_zombie_spawned;

function private on_zombie_spawned()
{
    // self is the zombie
    self.maxhealth = 500;
    self.health    = 500;
}

Note it is level-scoped. There is a similar-looking variable beside it that lives on game and therefore survives into the next map as a dangling pointer. Use the level one.

Hooking damage

zm::register_actor_damage_callback appends at runtime, so it is safe to add from an injected script. Return -1 to leave the damage alone. Any other value overrides it. Piggybacking damage is also the practical substitute for a spawn callback when you need to touch a zombie that was already alive.

Spawning a zombie somewhere specific

Two things must be right or you get nothing, or a zombie that appears and vanishes.

  • The spawner needs its force-spawn key set. spawn_zombie tests it first and returns having spawned nothing. It is a map key, not something the shipped scripts set. Set it on the spawner you are about to use, and try a few spawners.
  • Pass the spawn point as the third argument, and do not teleport afterwards. Every zombie runs its spawn think as it appears, which picks a spot from the map's zombie locations and drags the AI there, so a zombie you placed and then let spawn gets relocated out from under you. The location is claimed on the first call and every later call is ignored, so win the race by passing it in. A bare spawnstruct() with .origin and .angles and no script_noteworthy takes the arbitrary-point branch, which is the game's own way of putting a zombie exactly where you want it. A struct that does carry a script_noteworthy matches nothing and does not move at all, which is where the “invisible zombie” reading comes from.

Keep forceteleport only as an after-the-fact correction, gated on a bounded wait for the spawn-complete notify.

Rounds

  • Pause spawning by clearing the "spawn_zombies" flag. The round cannot end while it is clear, because the remaining count never drains.
  • Do not try to clear out zombies that are already alive. Enumerating them means getaiarray, and that crashes. Design around it: pause spawning and let the round drain, or kill through a damage callback.
  • Round health and count scale from level variables the game sets each round. Write them after the round has started, not before, or the round logic overwrites you.

Main quests

A quest's step state is ordinary script state, so a mod can move it, but each map keeps it differently and the steps have side effects the game expects to have run. Read the map's own quest script before moving anything, and expect to have to set up what an earlier step would have created.

What you cannot do

Every item here was tried in game and does not work. They are collected in one place so you can check before spending an evening, and most of them are the same fact wearing a different hat: the game seals what it can load when the map loads, and your script arrives after that.

Not possibleWhy, and what to do instead
Register a clientfield or client UI model The manifest is sealed at map load. Late registration (server side, client side, or both halves in the same load) produces a “Clientfield mismatch” kick for everyone. There is no ordering, no timing and no pairing that works. Set an existing field instead. That is safe and is how the two sides talk.
Flip a gametype setting that gates a clientfield registration Same kick, arrived at sideways: the host registers a field the joiners do not. Worse, the setting persists into later matches, so it keeps kicking after you stop loading the mod. A game restart is the only cure. The security scanner flags the known ones.
Add a model, sound, effect, animation or weapon asset There is no asset pipeline and no way to make the retail game load one. A script can name anything the map already loaded, and nothing else.
Give a cross-map weapon its audio You can register a wonder weapon on a map it does not belong to (the model resolves, the item works), but its sounds live in that other map's sound bank and no builtin loads one. It will be silent, and that cannot be fixed from script.
A custom powerup HUD icon The powerup row's UI only draws slots wired through the clientfield registration path, which is sealed. Writing the UI models directly executes and renders nothing. The ceiling is to borrow a live slot from the server side: wrong icon, real countdown.
Ship UI (LUI/Lua) of your own No way to ship UI files. UI work is limited to what GSC can drive on menus the game already has.
Maps, prefabs, Radiant, zone files None of it exists for Cold War. Anything you place, you place from script at runtime.
Call between the two VMs An injected .gsc and an injected .csc share nothing but already-registered clientfields. Derive what you need locally on each side.
getaiarray() / on_ai_spawned Hard crash. Use the level spawn hook and the damage callback.
Survive a map load Your mod is gone. Re-load it from the pre-game menu. Nothing you write can persist across it.
Tell a public match from a private one Measured in game, twice: a real Private-mode co-op lobby reports exactly what a matchmade one does on every session builtin there is. So a script cannot branch on lobby type, and neither can the launcher. Ask who is in the game instead. The test guard is built on that, and it is why there is no public-match block.

Before you press it

  • Updating is not a separate action. Submitting a project that is already published is an update. It is worked out from the project itself, not its title, so you can rename it freely.
  • The build that ships is not your test build. Submission compiles your source through its own path, without the test guard, which would kick anyone who joined your published mod.
  • Your package carries source, not a compiled script. That is deliberate: the settings system needs the source on the player's machine, and it means what a moderator read is exactly what runs.
  • A locally built package cannot be loaded. Approval is what makes a package loadable, which is why there is no local packaging page to mislead you into trying.
  • A rejection reaches you in the launcher, as a popup and in the notification bell, not in the review channel, which is moderators only.
  • Submitting again before a verdict replaces your pending submission instead of creating a second mod.

The security scanner

Every submission is scanned for what the mod could do to other players. You can see the report live on SUBMIT MOD before you send anything, and the same rules run again on the review side.

Nothing is blocked, but some things are shouted about

A rule marked blocking means HIGH ALERT, not STOP. You can always submit. What happens is that the review post gets a red alert naming the file, the line and the code, and the approval is deliberately made harder to give. The reason is honest: several of these calls are hostile in one use and completely ordinary in another, and no pattern match can tell which.

If you get a finding you believe is fine

Explain it in the NOTE FOR THE REVIEWERS box. It rides in the review post and nowhere else, not in the description, which ships in the package and is what every player reads. A one-line explanation of why your mod calls the thing it calls is usually all that is wanted.

Findings carry the file they came from, and each script is scanned separately. A line number into a merged script nobody wrote is not a location.

Collaboration and sync

Two people on one mod work on one shared copy. The owner invites from COLLABORATORS on the project card, and the invitation is accepted, in the invited person's own launcher, before anything is written. It can be revoked at any time.

One press does both directions: pull what the others have done, merge it into yours, then send yours back. It is one operation on purpose. Sending without pulling first is exactly how one person's next pull quietly removed their own work. GET LATEST FILES is the pull half alone.

How your mod reaches players

The MODS page is a catalogue: it lists every published mod, whether or not it is downloaded. Installed mods sit at the top, and everything else is under AVAILABLE TO DOWNLOAD, split into developer and community releases. So a player sees your mod before they have it, which is why the thumbnail, the title, the description and the tags are worth spending time on.

  • Your card shows the picture, its star rating, the title, your author name and up to three tags.
  • Your panel shows the full description, every tag, the mod's rating opposite the title, the current version with the dates it was first uploaded and last updated, a CHANGE NOTES button holding every release's changelog, the favourite count, and (once downloaded) your settings controls.
  • A rating is per mod, not per version, and one per person, so it needs a Discord sign-in. An update does not start the score again: a mod is one thing to the people rating it. Your changelog is what says the update is worth another look.
  • The stat that matters is favourites, not downloads. A download says nothing, but a star is somebody choosing to keep it.
  • Selection order is load order. If your mod is likely to collide with a common one, saying so in the description saves everybody a support conversation.

An update reaches players through the same page: their launcher notices the new version and offers it. Your setting values on their machine survive it, because they are keyed by your mod id, which is one more reason not to rename setting ids between versions.

Finding out how the game does it

Almost every question a Cold War mod raises (what is this called, what does it take, when does it fire) is answered by reading the game's own scripts. There is a full decompiled dump of them, and knowing how to work it is the single most useful skill in T9 modding.

The dump

github.com/ate47/bocw-source is Cold War's script and data dump. Its shape:

PathWhat is in it
scripts/zm_common/The shared zombies systems: rounds, perks, powerups, weapons, score, spawning. Start here. Anything in it works on every zombies map.
scripts/zm/Per-map scripts. Where a specific map's quest, boss or gimmick lives.
scripts/core_common/flag_shared, callbacks_shared, values_shared, array_shared, util_shared, the utilities you will #using constantly.
hashed/Scripts whose real names were never recovered. Plenty of live content is in here. Do not skip it because the file name is a hash.
tables/, scriptbundle/Data. Weapon lists, asset tables, tunables.

How to actually use it

  1. Find the thing by its player-visible string. Search for the hint text a machine shows, the notify name in a wiki, the model name you saw. That lands you in the right file faster than guessing at function names.
  2. Read who calls what. Search the whole tree for the function name. The callers tell you the argument types, what must be true first, and what the game expects to happen afterwards, which is usually the part that breaks a mod.
  3. Re-author, do not copy. Decompiled code is full of function_<hash> names and the occasional artefact. Read it for design and write your own.
  4. Recover opaque values from the data. When decompiled code reads struct.var_<hash>, that field hash is the same hash used as the key in the dumped scriptbundle data, so a tunable that looks unreadable in the script is recoverable from scriptbundle/ and tables/.

The dump is not retail, exactly

Struct and entity fields in particular do not always match the shipped game. A field the decompile shows being written may simply not be there in the build you are injecting into. Before building on one, probe it in game: print an isdefined() for it at the moment you would use it. And probe at the moment the thing is on screen, not at load time. Some fields only populate once it is displayed.

The same goes for the per-map asset tables. They are hints. A call that worked in game is the only proof.

Older Treyarch games, when Cold War is unclear

Cold War zombies is built on the codebase of the Treyarch games before it. Their decompiled scripts often have the same system with better-recovered names, and they are the reference for “how was this done originally” when you are recreating classic behaviour. Treat them as ancestors, not as documentation.

Hashed names

Cold War stores most identifiers as hashes instead of text, so anything the decompile could not resolve to a name appears as a prefix and a hex number: function_9c55db3, var_b8be892e, hash_4751990deae37e66.

You can write those names straight into your script. They are valid identifiers, the compiler understands them, and calling namespace_dd7e54e3::function_fe5f8894() works exactly as it would if you knew what it was called. Plenty of good mods are full of them.

Which prefix tells you which hash width

var_, function_, namespace_ and event_ are the 32-bit hash. hash_, script_ and file_ are the 64-bit one. It matters when you are trying to recover a name: you have to search the right width.

HASH FINDER

The fourth MOD TOOLS page, and it does three things:

  • Name to hash. Type a guess and see it under every algorithm at once. COPY AS gives you the four spellings you actually type into a script: #"name", the bare hash, the function_ form and the var_ form.
  • Hash to name. Paste anything a decompile wrote (with or without a prefix, with or without 0x) and get the name back if it is known.
  • Search the known names. A full-text search over the T9 names the database has, which is how you find the function you half-remember.

The workflow that matters is the guess-and-check one: you suspect var_b8be892e is something like custom_perks, so you type candidate names on the left and watch for the row on the right to outline green.

One trap if you compare against other tools: the common CLI prints the 64-bit hash masked, its UI prints it unmasked. The game uses the masked value, and that is what HASH FINDER calls XHash. The raw value is offered as a separate row.
